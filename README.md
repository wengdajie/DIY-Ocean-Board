# 海洋板 DIY · 榫卯 CAD 图纸生成器

一个**纯前端、离线可用**的参数化家具 CAD 生成器。三种用法：

1. **选结构配方填尺寸** —— **16 种**配方（家具 / 柜架 / 置物架 / 酒格四大类），榫卯全自动
2. **填零件清单 / 排板位** —— 自定义，含孔、洞洞板、四角、边缺口、定深铣槽
3. **直接上传一张图片** —— 自动描摹成轮廓件 + 底座，或切成等高分层叠件

接合方式有 **11 种**（指接 / 圆角 / 倒圆 / 斜接 / 燕尾 / 拼图 / 楔钉 / 卡扣 /
舌槽 / 木销 / 饼干榫），每种都有自己的能力矩阵（能不能用在角接 / 中部交叉 /
共面拼板），选不适用的会**自动降级并说清为什么**，不会默默出一张装不上的图。

输出带**榫卯结构**的可加工图纸（DXF / SVG），并完成**板材排样**（可锁纹理方向）与**料单核算**。

> 海洋板（船舶级多层胶合板）密度均匀、层间无空洞，特别适合做榫卯板式家具——
> 这也是本工具默认按"通榫 + 指接"出图的原因。

## 快速开始

双击 `app/index.html` 即可（无需安装、无需联网、无需服务器）。

推荐 Chrome / Edge。

## 功能

### 一、16 种结构配方，榫卯全自动生成

> **为什么没有"家具类型"这个概念了**：旧版把入口分成"5 种家具"和"自定义配方"
> 两套，但两边其实都是"填几个数→出一整件"，参数面板长得一模一样，用户却要先猜
> "我要的东西算家具还是算配方"。现已**合并成一个下拉框**，按四大类分组，
> 上方一排分类 chip 可筛选；每个配方自带**推荐尺寸**，换配方不会拿着上一个
> 配方的尺寸硬算（旧版从"长凳 1200×350×450"切到"不规则格柜"会得到一个 450 高的柜子）。

### 二、自定义（两条路径，从"填表格"到"排板位"）

> 上一版的自定义只有 3 个输入框 + 一个要手写 JSON 的板位表，打开还是空的，
> 基本没法用。本版**参照 [慧切 cutlist](https://www.smartcuttech.com/cutlist)
> 这类板材下料工具的交互**重做了一遍：核心思路是**先让不懂 CAD 的人能填表出图**，
> 再把"排板位自动求榫卯"作为进阶能力保留。
>
> 选中"自定义"会**自动跳到「结构编辑」标签页**，并预填一份"墙面层板 3 件套"——
> 打开就有东西可改，不再对着空白发呆。

#### 路径 1：零件清单（零 CAD 门槛）

**一行 = 一块板**，像填 Excel 一样：长 × 宽 × 数量 × 纹理 × 工艺。适合"我就是想切几块板"。

| 列 | 说明 |
|---|---|
| 启用 | 取消勾选 = 该行临时不出图（比对方案时不用删行） |
| 零件名 / 长 / 宽 / 数量 | 必填项就这四个 |
| 纹理 | 横纹（顺长边）/ 竖纹（顺短边）/ 不限 —— 会**约束排样旋转**，见下 |
| 四角 + 角尺寸 | 圆角 / 斜角(45°) / 方角切口，四角统一或单角指定 |
| 洞洞板 | 勾上填 孔径 / 孔距 / 留边 / 错排，自动排满整板并**整体居中** |
| 工艺（展开行） | 圆孔 / 矩形孔(可圆角) / 腰形孔(可转角) / 边部切口 / 定深铣槽 |
| 操作 | 复制、上移下移、删除 |

5 个一键模板：**宜家风格洞洞板** / **墙面层板 3 件套** / **桌面 + 走线孔** /
**抽屉面板 + 指拉槽** / **四角切口立板**。

孔位支持**基准点**（`ref`）：`bl` 左下（默认）/ `center` 居中 / `br` / `tl` / `tr`，
所以"距右边 50、距上边 30"可以直接写 `ref: tr, x: -50, y: -30`，不用自己算。

#### 结构配方（填参数，自动出整件）

见上面【一、16 种结构配方】。每个配方都有自己的参数表单（UI 按声明自动渲染，
改参数即时联动），包括 `select` 型参数（比如鞄架的"背板方式：无 / 通榫"）。

#### 路径 2：板位表（进阶，任意结构）

给出每块板在空间中的位置，程序**自动两两求交并布置榫卿**。不用写 JSON，也不用先理解坐标系。

**每块板就六个数**，所有板用同一组列，与朝向无关：

| 分组 | 列 | 意思 |
|---|---|---|
| **位置**（板的最小角） | 左起 X | 板的左边缘到柜体最左的距离 |
| | 前起 Y | 板的前边缘到柜体最前的距离 |
| | 离地 Z | 板的下边缘离地高度 |
| **尺寸**（三个方向的长度） | 宽 W | 左右方向 |
| | 深 D | 前后方向 |
| | 高 H | 上下方向 |

三个尺寸里**恰有一个等于板厚**（由朝向决定）。那一格会**自动置灰、虚线边、不可编辑**，
鼠标悬停会提示"这个方向就是板厚方向"。比如一张平放的层板，高 H 就是板厚；
一张竖放的侧板，宽 W 就是板厚。

其余列：

- **朝向**：下拉选`横放（层板 / 顶底板）`、`竖放（侧板 / 竖隔板）`、`竖放（背板 / 门板）`——
  不是 `XY/YZ/XZ` 这种代号。改朝向时程序会**保持这块板的位置不变**
  （以原位置中心为准，把板厚塔到新方向），不会一改就瞬移到别处
- **数量 / 纹理 / 四角 / 洞洞板 / 备注 / 工艺**：与零件清单模式完全一致
- 表头分两行：上行是分组（`位置（板的最小角）` / `尺寸（灰=板厚自动）`），
  下行才是具体列名；两组之间有竖分隔线，六个数字视觉上分块

配套能力：

- **智能加板**：`＋竖隔板` / `＋层板` / `＋背板` 会自动避开已占标高，
  并且**只跨一格而不贯通**（贯通会与隔板变成互穿搭接，与旁边已有的对接榫眼打架）
- 也可以从配方"展开"成板位表再手改（只读展示用的是同一组六列）

#### 三视图：拖拽调位 + 自动吸附 + 对齐/等间距

清单编辑区下方是正视(X-Z) / 俯视(X-Y) / 侧视(Y-Z) 三联图。
板面正对视图 = 浅色半透明，只看到板厚的侧面 = 实心深色，选中呈橙色并带四个握点。

**直接拖动矩形就能改板位**，不必回表格改数字：

| 操作 | 效果 |
|---|---|
| 在哪个视图里拖 | 就只动那两个世界轴（正视→X/Z，俯视→X/Y，侧视→Y/Z），第三轴纹丝不动 |
| 拖动中 | 实时画吸附参考虚线 + 底部提示"板的近端 贴 左侧板 的远侧面" |
| 松手 | 落点圆整到 0.1mm，重新求解榫卯，表格六列数字同步刷新 |
| 按住 **Alt** 拖 | 临时关闭吸附（真想放个难看的值时） |
| **Ctrl / Shift** 点 | 多选（三视图与表格圆点都支持），多选后拖动 = 整组平移，相对关系不变 |
| 点空白 | 取消选中 |

**为什么拖拽必须吸附**：手拖鼠标永远差几毫米，而家具板位几乎全是
"齐平 / 贴合 / 居中"。差 0.7mm 的层板图上看不出来，但求解器会判它和侧板
**不相交**，榫卯直接丢掉。吸附引擎四类候选线：

- `edge` 其它板的近/远侧面（最常用：把层板顶到侧板内表面）
- `center` 其它板的中线；`bounds` 整体包围盒两端与中线；`origin` 原点
- 板自己有**三个吸附把手**（近端 / 远端 / 中线），任一把手贴上任一候选线就算吸附
- **`edge` 有结构性优势**：开口 570 里放 569 宽的板时，"与整体中线对中"可能
  比"贴住侧板"更近，若纯比距离就会吸到中线 → 两边各留 0.5mm 缝 → 榫卯全丢。
  所以给非 `edge` 类别按容差比例加罚分

**对齐工具条**（板位表模式专属，分左右/前后/上下三组，每组 5 个按钮）：

| 按钮 | 需选中 | 作用 |
|---|---|---|
| 左/右、前/后、底/顶 对齐 | ≥2 块 | 选集的该侧边缘全部对到同一坐标 |
| 左右/前后/上下 居中 | ≥2 块 | 全部以**中线**对到选集包围盒中线 |
| **等间距** | ≥3 块 | 首末不动，中间重排使相邻**净空完全相等**——一排层板的层高一致，这就是"间隔对齐" |
| **中线等距** | ≥3 块 | 按板的**中线**等距，适合格栅条 / 打孔阵列 |

两种分布必须分开：板厚不一致时，"中线等距"算出来的净层高是不相等的，
而家具上人眼看到的是净空。工具条还会报"移动了几块 / 净空多少 mm / 选集跨度"。

几何部分全是**纯函数**（`Custom.snapLinesFor / snapAxis / movePanel /
alignPanels / distributePanels / selectionExtent`），不碰 DOM，便于单测。

求交后按接触类型自动选择接合方式：

| 接触类型 | 处理 |
|---|---|
| 互穿（cross） | 双向半槽搭接，各切板宽一半，且**开口方向相反**（否则物理上插不进去） |
| 对接（butt） | 子板出通榫，母板开通榫眼 |
| 端对端（corner） | 互补指接（phase 0/1 交错咬合） |

角接位置会自动避开"榫眼跨出板边"的非法情况——改用指接而非通榫眼。
若某条板边被多处接合同时抢用（真实的过约束），会**降级成能切出来的合法零件**，
并明确提示"保留了哪几处、放弃了哪几处、放弃处请改用木销或自攻螺丝"。

#### 加工特征库（清单模式与板位表模式通用）

| 特征 | 说明 |
|---|---|
| 圆孔 / 矩形孔 / 腰形孔 | 矩形可圆角；腰形可指定总长、宽与旋转角 |
| 洞洞板阵列 | 孔径 / 孔距(可分 X/Y) / 留边 / 砖砌错排 / 局部删孔；阵列整体居中 |
| 四角处理 | 圆角 / 斜角 / 方角切口，去料量恒为 `notch > chamfer > round` |
| 边部切口 | 任一边上开缺口，`at` 一律按"自然视图"理解（上边从左起算、左边从下起算） |
| **定深铣槽 pocket** | **不切透**，深度 < 板厚。走 `POCKET` 独立图层，不计入净面积但计入切割长度 |

安全检查会挡住：孔越出板边、孔距板边不足、切口互相重叠、切口压到四角处理、
切口几乎切穿整板、铣槽深度 ≥ 板厚（那是切透不是铣槽）。

#### 纹理方向（排样会真的遵守）

海洋板有明显的表层纹理，横竖用错在成品上很扎眼，承载方向也不同。

- 每个零件可标 **横纹（顺长边）/ 竖纹（顺短边）/ 不限**
- 勾选"遵守纹理方向"后，排样**只允许不破坏纹理的旋转**：
  横纹件的 +x 必须平行大板长边，竖纹件必须垂直
- 排样图上会用一组细平行线画出纹理走向，一眼看出方向对不对
- 会汇报"因纹理被锁定旋转的零件"，方便判断利用率损失来自哪里

#### 板材厚度（自由输入，不再是六个选项）

板厚输入框可**直接填任意值**：`3～60mm`，`0.5` 步进，**支持小数**（16.5 / 13.8 / 22.3 都行）。
旁边另有 `9 / 12 / 15 / 18 / 21 / 25` 六个常用厚度 chip，只是快捷填值，真正的值永远以输入框为准。

> 旧版这里是 `<select>`，只能选那六个值 —— 填 16.5 会**静默变成空串**，
> 于是 `t = 0`、榫宽全为 0、整张图红报错。这是本轮修掉的真实缺陷之一。

自由输入必然会有人填空 / 填 0 / 填 500，所以入口处统一夹住并**明确告知**：

| 输入 | 处理 | 提示 |
|---|---|---|
| 空 / 非数 / ≤0 | 按 15mm 计算 | 红底警告条 |
| < 3 | 夹到 3 | 红底警告条，写明实际用值 |
| > 60 | 夹到 60 | 红底警告条，写明实际用值 |
| 正常值 | 原样使用 | 灰字说明"当前板厚 xx mm" |

改板厚后榫宽 / 榫眼 / 槽宽 / 零件厚度 / 板位表的厚度轴**全部跟着重算**，
测试用 `榫眼短边 ≈ t + fit` 卡死这一点（这是"真的能切出来"的硬指标）。

**厚板连带修掉的一个缺陷**：`背板内缩` 默认 15mm，而背板榫眼宽 = `t + fit`
以内缩值为中心开在顶/底/侧板上。板厚一旦 ≥ 26mm，榫眼就跨出板边 →
`box` / `bookshelf` 报 8 条"孔越出板边"。现已按 `(t+fit)/2 + 15%t` 夹住下限，
并给一条 warn 说明"已自动改为 xx mm"，而不是默默改或直接报错。

#### 实测板厚补偿

标称 15mm 的海洋板实测常在 14.5–15.5mm 之间，直接按标称值开榫眼必然松或紧。

板材区可填**实测板厚**（0 = 用标称值）：填了之后所有榫眼宽按
`实测板厚 + fit` 计算，零件厚度也按实测值走，并在提示区标明"已按实测 xx.x mm 补偿"。
实测值**优先于**上面的板厚输入框（`nominalThickness` 会保留标称值供料单参考）。

### 三、上传图片自动生成

支持三种投喂方式：**拖入虚线框** / **点击选择文件** / **`Ctrl+V` 粘贴**（也可直接拖到画布区）。
内置两个示例图可一键试用。

#### 模式 1：轮廓件 + 底座（立牌 / 摆件 / 门牌）

按剪影切一块板，**底部自动出榫**，并配一块开好榫眼的底座：

- 自动找"着地面"（最低那几列材料），在上面生成居中的榫头
- 底座尺寸自动（宽 = 件宽 + 2×外扩，深可自动取 0.28×高），四角圆角
- 底座榫眼宽 = `板厚 + fit`，与榫头逐个对位
- 图中的封闭白区（如窗户）会自动识别为**挖孔**，孔归属到"包含它且面积最小"的形状

#### 模式 2：等高分层（浮雕 / 等高线 / LOGO 立体化）

按灰度把图切成 N 片叠起来，越深越靠底层：

- 层数 2–12，自动生成台阶状轮廓（面积逐层递减）
- **层间对位销孔**：在所有层的公共区域内自动找两个相距最远的位置打孔（配 φ6 木棒/竹签）
  - 销孔位置在**面积最小的那一层**内部撒点，再逐层用圆周取样验证，确保每层都打得下
- 自动汇报叠层总高 = 层数 × 板厚

#### 二值化与描摹参数

| 参数 | 说明 |
|---|---|
| 自动阈值 | Otsu 类间方差最大化；结果会回填到滑块供继续微调 |
| 阈值 | 1–254 手动滑块，拖动即自动取消"自动" |
| 反相 | 取白色区域（用于白图黑底） |
| 只用透明通道 | **PNG 透明底的图勾这个最准**，完全不看颜色 |
| 去噪强度 | 按图面积比例删小斑点 + 填小孔（与画布边框连通的背景不填） |
| 简化容差 | Douglas-Peucker 容差（mm） |
| **保角平滑** | 见下 |
| 目标宽 / 高 | 两个都填 = 等比缩放取小者；填 0 = 该方向不限制 |

**关于"保角平滑"**：裂缝追踪出来的轮廓全是 90° 像素锯齿。单纯用 DP 简化时，
若容差略小于台阶高度就压不平，斜边上会残留大量"楼梯"顶点（五角星实测 **90 个点**）。
本工具的做法是：

1. 先用 2× 容差做一遍 DP，把**结构性拐角**（星角、直角）标记为固定点
2. 其余点做 `[1,2,1]/4` 加权平滑，把锯齿抹成近似直线/圆弧
3. 再用目标容差 DP 简化

结果：五角星 **90 → 11 个点**（面积误差 <0.4%），圆约 32 点（误差 0.09%），
而**矩形仍精确 4 点、十字仍精确 12 点**（内凹角一个不丢，否则搭接会失效）。

#### 图片预览页（像素级反馈）

新增"图片预览"标签页，三种显示方式：**叠加**（原图 + 半透明掩膜）/ **掩膜**（纯黑白）/ **原图**，
并把**描摹结果的绿色轮廓**叠在原图上——让你切之前就能确认阈值到底切出了什么形状。
带透明棋盘底、像素尺寸与当前阈值标注。

#### 图片选材建议

- **线稿 / 剪影 / 纯色图形效果最好**；照片请先自行去背
- PNG 透明底 → 勾"只用透明通道"
- 等高分层需要图本身有**明确的灰度层次**（渐变、等高线、浮雕图）
- 立牌记得留出"着地面"（底部有一段平的实料），否则榫头会长在奇怪的地方

### 四、榫卯参数

#### 11 种接合方式

| 样式 | 能用在 | 额外参数 | 说明 |
|---|---|---|---|
| 指接（直榫 / box joint）| 角接 + 中部 | — | 默认；最通用，激光/CNC 都好切 |
| 圆角榫头（round）| 角接 + 中部 | 榫头圆角 R | 榫头端头倒圆，插入时容错更大 |
| 根部倒圆（fillet）| 角接 + 中部 | 榫头圆角 + 根部圆角 | 根部倒圆卸应力，不易开裂 |
| 斜接榫（mitre）| 角接 + 中部 | 倒角量 | 榫头带 45° 倒角，押缝更好看 |
| 燕尾榫（dovetail）| **仅共面拼板** | 张角 5–20° + 根部圆角 | 自锁；90° 角接下**几何上不可能**，证明见下 |
| 拼图榫（puzzle）| **仅共面拼板** | 颈部半径 + 根部圆角 | 四角互补哬合，拉不开 |
| 楔钉榫（wedge）| 中部交叉 | 榫头伸出 + 楔槽宽 + 楔度 | 通榫穿出后打楔钉，**可拆装** |
| 卡扣（snap）| 中部交叉 | 倒钩高 + 倒刺 + 弹片缝 | 弹片卡扣，不用工具 |
| 舌槽（tongue）| 中部 | 槽深 | 定深铣槽（不切透），适合背板/底板 |
| 木销（dowel）| 角接 + 中部 + 平面重叠 | 销径 + 销数 | 靠 φ6/φ8 木棒定位，外观无榫 |
| 饼干榫（biscuit）| 角接 + 中部 + 平面重叠 | 饼干宽/长 + 槽深 | 樭榫机开橄榄形槽 |

能力矩阵是**显式布尔**（不允许 undefined 兜底）：选了不适用的组合会**自动降级到
指接并弹一句说清为什么**，而不是默默出一张装不上的图。

##### 为什么 90° 角接的燕尾榫在平板直刀下不可能

证明写在 `joints.js` 的 `tabProfile` 头部：角部公共区记作 `(u, p, q)`。
A 是平板直刀通切，它的切割轮廓沿 `p` 方向恒定（只随 `q` 变）；B 同理只随 `p` 变。
两者的分界面 `u = f_A(q)` 与 `u = f_B(p)` 要想**既不重叠也不留缝**，必须处处相等——
一个只随 `q` 变的函数等于一个只随 `p` 变的函数，**只能两边都是常数** → 只能是直榫。

想要 90° 自锁，请用：**拼图榫**（共面拼板）/ **楔钉榫** / **卡扣** / **钩形搭接**。

#### 其余

- **燕尾角度**可调 5–20°
- **榫齿宽**：自动（≈2.2×板厚）或手动指定；**齿数强制为奇数**，保证花纹左右对称、
  配对件用 phase 0/1 严格互补
- **配合间隙 fit**：定义为**总间隙**（榫与槽之间的全部松量）
  - 沿边长方向：榫每侧收 `fit/4`、槽每侧放 `fit/4`
  - 厚度方向：榫眼宽 = `板厚 + fit`
  - 之所以取 `fit/4`：指接的**两个**配对件都会被收窄，若各让 `fit/2` 实际会松一倍

### 五、加工补偿

- **激光**：无需内角让位
- **CNC 铣削**：圆刀无法铣出内直角，方榫会插不进去，故提供
  - **Dogbone**：角点处 270° 过切圆
  - **T-bone**：沿边开矩形耳槽
  - 让位半径 = 刀具半径，自动只作用于**内凹角**（凸角不动）
- **kerf 刀缝补偿**：导出时外轮廓外扩 `kerf/2`、孔内缩 `kerf/2`，使成品达到公称尺寸；
  定深铣槽同样**内缩** `kerf/2`（否则槽会铣宽，配合件插进去就松了）

### 六、排样与导出

- 货架式装箱（高度降序 + 首次适应），支持 90° 旋转、板边留白、零件间距
- 常用幅面预设（2440×1220 等），实时利用率统计
- 导出：
  - `DXF`（R12/AC1009，最大兼容性；POLYLINE + bulge 保留真圆弧；
    **CUT / MARK / POCKET 三层分离**——`POCKET` 层是定深铣槽，附 `D<深度>` 文字标注，
    交给师傅时不会被误当成切透线）
  - `SVG`（mm 实尺寸，`evenodd` 正确挖孔）
  - `CSV` 料单（12 列：序号/零件名/数量/长/宽/板厚/**纹理方向**/**通孔数**/**铣槽数**/面积/切割周长/备注；含 BOM 头，Excel 直接打开不乱码）
  - `CSV` **加工清单**（每个孔/槽一行，带零件内坐标、类型、尺寸、深度、是否切透）
  - `JSON` 参数存档（含图片模式的阈值/尺寸，以及自定义的清单行/板位表/配方参数）
  - **导出全部**：上述 6 个文件一次写完

#### 导出位置（路径选择）

> 浏览器**永远拿不到绝对路径字符串** —— 没有任何 API 能把 `D:\xxx\yyy` 告诉网页（这是
> 沙箱限制，不是没实现）。能做到的只有 File System Access API 给的**句柄**。
> 所以这里分三档，且每一档都在界面上**把东西到底落在哪里写成人话**。

| 档 | 条件 | 行为 |
|---|---|---|
| **直写文件夹** | 点过「选导出文件夹…」| 之后所有导出**不再弹框**，直接写进去；"导出全部"一次落 6 个文件 |
| **另存为对话框** | 未选文件夹 + 勾了"每次问" | 弹原生另存为，**带类型过滤器**（免得存成无后缀文件）|
| **默认下载目录** | 都没有，或浏览器不支持 | 走 `<a download>`，仍然能导 |

几个必须做对的细节（都有断言盯着）：

- 用户点**取消**（`AbortError`）是正常操作：不报错，也**绝不偷偷降级成下载**
  （用户刚明确说了不存，结果东西落到下载目录 = 比报错更坏）
- 非取消类**硬错**（`SecurityError` 等）才降级成下载，且把原因报出来
- 文件夹**句柄失效**（目录被删 / 权限过期）→ 丢掉死句柄 + 降级下载 + 提示重选，
  而不是下次拿着死句柄再失败一次
- **没选文件夹时的"导出全部"直走下载**：浏览器只允许一个用户手势弹一个文件对话框，
  连弹第二个开始直接 `NotAllowedError` → 那就成了"点了导全部只得到一个文件"
- 选定文件夹后"每次问"**自动置灰**（留个勾了没反应的框比什么都不做更坑人）
- 零零件时 DXF/SVG/CSV 全部**拦住并说明原因**，但参数 JSON 仍可导
  （用户可能就想存一份现场参数去问人）
- 文件夹句柄存在 **IndexedDB**（句柄不能 `JSON.stringify`，localStorage 存不了）；
  重新打开页面后权限会降成 `prompt`，所以启动时先 `queryPermission` 确认还是
  `granted` 才直接用，否则提示重选（不主动 `requestPermission` —— 那必须有用户手势，
  启动时调一定被拒）

注：`file://` 直开时浏览器**不开放** File System Access API，会自动走第三档，
并在按钮 `title` 里说清原因（需 Chrome/Edge 且用 http(s) 打开）。

### 七、视图

- **排样图**：滚轮缩放、拖动平移
- **零件详图**：每件独立成格，标注尺寸与孔数
- **3D 装配**（本轮重写，见下）
- **图片预览**：原图 / 掩膜 / 轮廓叠加（仅图片模式）
- **结构编辑**：清单表格 / 板位表（位置 XYZ + 尺寸 WDH 六列，板厚那格自动置灰）
  + **三视图**（可点选、**可拖拽**、可多选对齐，仅自定义模式）
- **料单**：表格 + 合计

#### 面板大小可拖拽

两根分隔条：左侧**参数栈 ↔ 图纸区**（竖向）、清单表格 **↔ 三视图**（横向）。

| 操作 | 效果 |
|---|---|
| 拖动 | 实时改尺寸，松手写入 `localStorage`（下次打开还是你拖完的样子）|
| 双击 / `Home` | 单轴复位 |
| `←/→`（竖）`↑/↓`（横）| 每次 ±16px（`Shift` ±48px），给鼠标拖不准的人 |
| 头部「布局复位」| 两轴同时回默认 |

两个容易做错的地方（都有断言）：

- **拖完必须重绘**。canvas 是 `width:100%/height:100%` + dpr 重设位图，只改 CSS
  不重绘就只是把旧位图**拉伸**（模糊 + 比例尺错）。所以断言盯的不是"宽度变了"，
  而是 `cv.width === round(cv.clientWidth * dpr)`。
- **夹紧边界要把"兄弟元素"扣掉**。三视图占高存的是百分比（窗口变高不走形），
  但 `#editPane` 里除了表格和三视图还夹着工具条/对齐条/分隔条本身（实测 ~57px）。
  直接用 `(h-180)/h` 作上限会让表格只剩 123px（还不到两行）。
- 从 `localStorage` 读回的值可能是**上次大窗口**存的 → 必须重新夹一次，
  否则小窗口下侧栏会把整个图纸区吃掉，而且没地方能拖回来。
- 清单模式没有三视图 → 横向分隔条**跟着隐**（否则表格底下挂一根拖不动任何东西的条）。
  这个显隐放在 `syncVis` 而不是 `Editor.drawPlan`：`generate()` 在零零件时会提前
  return，根本转不到 `Editor.render()`。

#### 3D 装配：真相机 + 挤出实体

不是"画一堆长方体"，而是把每块零件的**真实轮廓沿板厚挤出**，所以
**榫头 / 榫眼 / 指接齿在 3D 里看得见**（旧版每块板都是 6 面盒子，接合处一片平整，
看着像用胶粘的）。孔是真的挖穿的（孔中心像素 alpha = 0，有断言盯着）。

| 能力 | 说明 |
|---|---|
| 相机 | `D3.cam(ang, tilt)` 给出 right/up/fwd 三正交基（正交性误差 < 1e-9），投影与深度共用同一套基 |
| 深度排序 | **沿视线方向**逐面排序。旧版用 `x+y+z` 当排序键，与视线无关 —— 转到 `ang>180` 后前后关系整个反转，远板画在近板上面 |
| 光照 | Lambert：`shade = 环境 + (1-环境)·max(0, n·光向)`。旧版按"面的序号"查固定亮度表，转视角时同一物理面亮度不变，立体感是假的 |
| 背面剔除 | 按 `n·fwd ≥ 0` 剔除（旧版只看屏幕面积符号，没考虑相机位置） |
| 地面阴影 | 俯仰角够大且非爆炸态时投一层淡影，帮判断"哪块在底部" |
| 选中 / 悬停 | 点选高亮 + 加粗描边，HUD 报板名 / `宽×高×厚` / 孔数 |
| 命中测试 | `hit(px,py)` 从最靠前的面往后找；**孔中心正确返回 null**（不会点到被挖掉的地方） |
| 性能挡板 | `W` 键切"实体 / 盒体"，零件极多时退化成长方体更快 |

交互：拖动旋转 / 滚轮缩放 / `Shift+拖动`平移 / `E` 爆炸开关 / `+`/`-` 渐进爆炸 /
`1` 等轴测 `2` 正视 `3` 侧视 `4` 俯视 / `W` 实体切换 / `Esc` 取消选中。
右上工具条有 4 个视角预设 chip 与爆炸滑块，键盘改了也会同步回工具条。

（立牌会真的立在底座上；分层件会逐层 +板厚 叠起来。）

### 八、界面主题

整体是**暖白（warm white）**：底色带一点米黄，呼应海洋板本身的木色，长时间看不刺眼；
强调色用琥珀棕，蓝色留给"零件 / 图纸"这类工程语义，橙色统一代表"选中"。

颜色不只是好看。浅底比深底更容易出现"看得见但费眼"的文字，所以测试里加了
**WCAG 对比度扇扫**：扫所有可见文本节点，正文 ≥ 4.5:1、大字 ≥ 3:1，
并单独卡 hover / 选中行 / 提示条这些不在当前 DOM 状态里的配色组合；
Canvas 侧另有像素断言盯住"没有深色残留"。
这组断言当场抽出了 3 个真实可读性缺陷（见下文「被测试逼出来的真实缺陷」）。


`make_dump.py` 为什么不是一行 PowerShell：中文输出在 PS 管道里很容易被重新编码成乱码；
HTML 实体必须**先反转义 `&amp;`** （否则 `&amp;lt;` 会被错阶成 `<`）；且存盘前应先
`json.loads` 验一遗 —— 否则存下一个坏文件，下一步才报错，那时已分不清是生成错了
还是校验器错了。

### 被测试逼出来的真实缺陷（不完全列举）

本轮（家具类型并入配方 + 可拖拽布局 + 导出路径）：

- **`mirrorProf` 把弧段 bulge 归属的顶点错了一位**——静默出废图，仅影响带弧样式。
  环的存储约定是"`b` 挂在弧的**起点**上"（`loop[i].b` 描述 `loop[i]→loop[i+1]`）。
  镜像+反向后遍历方向变了，原来的起点变成终点 → **`b` 必须往后挑一个顶点**；
  同时镜像翻一次手征、反向又翻一次 → **两次抵消，符号不变**。旧版恰恰反了两头。

  后果实测（`bench` t=15 / `fillet` / 1200×350×450）：板腿上边榫头根部倒圆本应向内凹
  （削掉榫头自己的料），镜像后弧心跑到外侧 → 轮廓向内凹进 5mm（y 从 435 凹到
  **414.8**），把本该是材料的区域挖成空；于是同位置的榫眼落在空气上 → 被剔除 →
  **板腿只剩 1 个榫眼、坐面却照样出 2 个榫头 → 装不上**。
  变异测试已验证：`finger` 完全正常（纯直线）、`fillet` 报 2 错、**`round` 不报任何错
  但默默切错了弧**（minY=430.81）。

- **6 个早期配方没声明 `dims`**：它们只在 `panels()` 内部写了 `num(p.width, 900)`
  这种兜底默认，对外没有 `dims` → UI 换配方时不换尺寸。实测：从"长凳"
  （1200×350×450）切到"不规则格柜"，会得到一个 **450 高的"柜子"**，新竖隔板
  只能跳 424mm。已固化为硬指标"每个配方都必须有推荐尺寸"。

- **build 型模型一个接合数都不报**：UI 统计条与测试的"有接合"断言只认
  `info.tenonJoints` / `info.lapJoints`。家具模型原本一个都不报 → 家具类型并入配方后，
  右侧统计条会在 16 种结构里**念 5 种不显示接合数**。

- **`JSX_FIELDS` 漏声明导致整页白屏**：`Uncaught ReferenceError: JSX_FIELDS is not defined
  (app.js:912)`。坑在于**光看 DOM 看不出页面已经崩了** —— `__app` 是 undefined
  但页面结构照样在。后来固定用 `--enable-logging=stderr --v=1` 抓 CONSOLE 行。

- **三视图分隔条在清单模式下残留**：最初把显隐放在 `Editor.drawPlan` 里，
  但 `generate()` 在零零件时会提前 return，根本转不到 `Editor.render()` →
  切到空的板位表时分隔条会停在上一个状态。改到 `syncVis`（纯 UI 事，与生成成败无关）。

- **`clampPlan` 的上限忘了扣"兄弟元素"**：`(h-180)/h` 看着对，但 `#editPane` 里除了
  表格和三视图还夹着工具条/对齐条/分隔条本身（实测 ~57px）→ 拖到顶时表格只剩 **125px**，
  还不到两行。断言直接要求"表格仍留 >=180px"当场拓出来。

- **test-visual 两处只改 `.value` 不派 `change`**：旧写法只改 DOM 不改 `state.recipe`，
  以前默认配方恰好是 grid 所以巧合能跑；家具并入后默认变成 `box`（build 型无板位表）
  → `panelsOf` 返回 `[]` → `drawPlan` 返回 null。

榫卯 / 几何：
- `fit` 被两个配对件各让一次导致**实际松一倍**（test-mate 的间隙实测发现）
- 榫槽紧贴板边时与相邻边**共线重合**产生非法轮廓（改为由配对件 phase 处理转角）
- 通榫分格未内缩导致**榫眼开到板外**（Part.validate 的"孔越出板边"检查发现）
- T-bone 让位方向取反，**加料**且自交
- `loopArea` / `loopBBox` 用离散近似不准 → 改为弓形面积解析解 + 圆弧极值点

图片描摹：
- **Otsu 在纯黑白双峰图上所有阈值等价**，取首个最大值会返回 0（整图全黑）
  → 改为取并列最优区间的中点
- 外轮廓/孔的判定在 y 翻转后**反号** → 改为先在图像坐标系判定再翻 y
- 分层阈值方向搞反，塔尖跑到底层
- 对位销孔原先取"最后一层"，在台阶形上会打到别层的空处

自定义求解：
- 相交判定用严格 overlap，导致"层板端面顶住侧板内表面"（仅相切）被判为**不相交**
  → 加入带公差的 `touch()`
- 角接位置用通榫眼会**跨出板边** → 改用互补指接

自定义重构（本轮）：
- **边 profile 未按 u 排序**：一条板边上有多处接合时，段的顺序取决于板对枚举顺序
  （`i<j`）而不是 u 从小到大。镜像边（top/left）几乎必然逆序 → **轮廓折回自己**
  → "外轮廓自交"。L 形转角柜、井字酒格全炸。改为每条边保存**段列表**，
  生成时统一排序 + 检测重叠
- **两块板的半槽从同一物理侧切入 → 物理上插不进去**。最隐蔽的一个：
  `validate()` 完全查不出来（几何都合法）。根因是局部 `left/right/top/bottom`
  在不同平面可能指向同一世界方向（YZ 板的 right 和 XY 板的 top 都是 y=max）。
  正解：沿**交线轴**统一定向，一块从低端切入、一块从高端
- **搭接槽的长轴与定位轴整个串轴**：交线沿 u 时槽长轴应是 u、位置沿 v，原来写反
- 榫眼落进搭接缺口里（那块料已经被切掉，孔开在空气上）→ 主动剔除 + 点名是哪两块板打架
- `deskTop` 模板的走线槽用 `ref: bl, x: 0` → 一半在板外（改 `ref: center`）
- 新层板默认贯通整宽 → 与竖隔板变互穿搭接 → 与已有对接层板的榫眼打架；
  `＋竖隔板`同理会贯通全高。两者都改为**只跨一格**
- 配方参数只接受数组，直接塞字符串（JSON 导入 / 外部脚本）会崩在 `.slice().sort()`
  上；未知配方名会**悄悄退化成格柜**而不报错。改为库内统一 `normParams` 规范化 +
  未知配方明确报错
- **排样图的纹理平行线画在孔上面**（裁剪区没排除孔）：洞洞板上某一行孔恰好落在
  一条纹理线上，那一整行看起来就"没挖通"。像素断言逐孔验证时揪出来的
- 过约束（一条边被多处接合抢用）原先报 `error` 阻断出图，但降级后的零件其实
  完全能切 → 改为 `warn` 并说清"保留了哪几处、放弃了哪几处、放弃处怎么固定"

暖白主题 + 板位表直观化（本轮）：
- **`--dim` 在所有暖白底上都达不到 WCAG AA**（3.03–3.87:1）。侧栏标签、统计栏、
  Canvas 里的次要文字全用它——深底时很清楚，换浅底后变成了"看得见但费眼"。
  压深到 `#6b6152`（四种底色 4.67–5.98:1）
- **`--acc` / `--acc2` 当实心按钮底时，上面的白字只有 3.65 / 3.99:1**。
  深色主题时主按钮是"浅字深底"，暖白后这两个色反而成了全局最亮的"深色"，
  亮度被顶到临界。各压深一档（`#96651f` / `#26805e`，hover 更深）
- **块面色不能直接当文字色**：徒标的绿、删除按钮的红把 `--acc2` / `--err`
  拆到浅底上只有 3.3–3.9:1 → 拆出专用的 `--acc2-ink` / `--err-ink`
- 三视图"面 vs 边"的区分断言原本比**亮度**：深底时"实心"= 蓝通道更高，
  暖白底上"实心"反而更暗，判据整个失效 → 改比"蓝味"（b−r），与底色深浅无关。
  同时发现旧断言在**真实柜体上采样根本不可靠**（侧视里整张侧板盖在所有层板
  上面，半透明叠加后采到的永远是混合色）→ 另搭两块不重叠的最小场景去验
- 描摸轮廓绿从 `#35c88f` 改深后，旧的 `g > 140` 硬阈值不再成立 → 测试顶部集中
  定义 `THEME` 主题色常量，阈值从常量推导，下次换主题只改一处

3D 装配重写（本轮）：
- **深度排序键用 `x+y+z`，与视线方向完全无关**：绕到 `ang>180` 后前后关系整个
  反转，远板画在近板上面。探针实测 `ang=270` 时正确近板是 front，旧键却永远给 back
- **明暗按"面的序号"查固定表** `[0.55,1.0,0.72,...]`：转视角时同一物理面亮度不变，
  立体感是假的；转到背面还更亮。实测 `ang=0/90/180/270` 顶面颜色几乎不变。
  改为 Lambert `n·光向`
- 背面剔除只看屏幕面积符号，未考虑相机位置；`hue` 变量算了但从未使用（死代码）
- **每块板都画成 6 面长方体，榫头/榫眼/指接齿全看不见** → 改为沿板厚挤出真实
  outer + holes（2 个带孔端面 + 外轮廓每段边一个侧壁 + 每个孔每段边一个内壁）

三视图拖拽 + 对齐（本轮）：
- **`#alignBar` 的 CSS 默认是 `display:none`，而 JS 写 `style.display = ''`
  会退回 CSS 规则 → 对齐工具条从来没显示过**。更糟的是首版 e2e 断言写的是
  `style.display !== 'none'`，而 `''` 确实不等于 `'none'` —— **断言假绿**。
  改为查 `getClientRects().length` 与 computed display，并做了变异测试确认
  这条断言真能抓到（把 `'flex'` 改回 `''` 后立刻 FAIL）
- **吸附纯比距离会挑错线**：开口 570 里放 569 宽的层板拖到 x=15.7 时，
  "与整体中线对中"（差 0.2）比"贴住右侧板内表面"（差 0.3）更近 → 吸到中线 →
  两边各留 0.5mm 缝 → `intersect` 判不相交 → 榫卯全丢。而用户拖到那里的
  真实意图几乎必然是"顶到侧板"。改为给非 `edge` 类别按容差比例加罚分
- **拖拽落点不圆整**：屏幕像素反算出来的坐标是 `514.2977528089888`，
  导出到 CSV/DXF 里师傅没法读 → 松手时统一圆整到 0.1mm
- **多选一起拖时不能各自吸附**：若每块板独立吸附，相对关系会被吸附量拉散。
  改为只让主选吸附，反推真实位移后整组平移
- 吸附候选线必须排除"正在一起被拖的其它板"（它们也在动，参考自己毫无意义）
- **置灰按钮用 `opacity:.45` 淡到 1.70:1**，完全读不清 —— 而用户正需要读它才知道
  "原来还有这些对齐方式，多选两块就能用"。改为背景变灰 + 文字仍达 AA。
  顺带发现主题扇扫**没算 opacity**，一律拿原始 `color` 比 → 这类缺陷永远假绿，
  已给扇扫补上 alpha 合成
- **`distributePanels` 必须分"净空等距"与"中线等距"两种**：板厚不一致时二者结果
  不同，而家具上人眼看到的是净空（一排层板的层高）

板厚自由输入（本轮）：
- **`#thickness` 是 `<select>`（9/12/15/18/21/25），塞任何不在列表里的值会静默
  变成 `""` → `readParams().thickness = 0` → 榫宽全 0、整张图红报错**。
  用户要"板材厚度自定义输入"正是因为这个。改为 number 输入 + 常用值 chip
- **`backInset` 默认 15mm 与厚板冲突**：背板榫眼宽 = `t + fit`，以内缩值为中心
  开在顶/底/侧板上，`t ≥ 26` 时榫眼跨出板边 → `box`/`bookshelf` 报 8 条
  "孔越出板边"。注意直接调 `Models.box({thickness:30})` **不报错**（默认
  `backInset = t = 30` 正好安全），只有 UI 传了 15 才炸 —— 所以只测库不测 UI
  会漏掉。改为按 `(t+fit)/2 + 15%t` 夹住下限并给 warn

桌 / 凳（Python 交叉校验发现）：
- 腿架"中间挖一个大洞"，洞底边与板底边**共线重合** → 退化轮廓，切割会走出废件
- 更要命：横撑要从**深度中央**穿过腿架，而中间挖洞正好把那块料挖掉了，
  **横撑榫头会插进空气里** → 改为 I 形（竖柱 + 两侧镂空），中央始终是实料
- 横撑肩距少减了 `2t`，装配时会**顶死**

轮：上 GitHub 后 CI 在 Linux 上跑出来的

- **一条断言把"不标板名"验成了"文字有像素"**。本地 Windows 全绿，
  推上 GitHub 后 CI 红了**恰好 1 项**：`三视图: 多选时不标板名`。
  旧写法是数深橙色（`#a5620c`）像素，判 `two < one`。本地实测
  `one=216 / two=0`—— 那 216 全来自板名文字。而 Linux headless
  **常见没装 CJK 字体**，板名画出来是空白 → `one` 也是 0 →
  `0 < 0` 为假。**断言挂在了"当前系统装了中文字体"这个无关前提上。**
  改成拦截 `ctx.fillText` 直接量"到底调了几次、写的是什么"，
  与字体 / 拗键齿 / DPR 全无关。
- 而且新插针**当场拓出了我自己写错的预期**：按"单选只写 1 次"断言直接红，
  实测是 `[左侧板,左侧板,左侧板]` —— **三个视图格各标一次**才对。
  改成断 `n1.length === plr.views.length` 且每个都等于选中板名。
  变异验证：`selN === 1` 退回 `selN >= 1` → 当场 2 项转红并报出具体写了哪些名字。
- **CI 失败时匿名拿不到日志**（`GET /actions/runs/<id>/logs` 返 403），
  但 **annotations 接口是公开可读的**。于是让 `ci_run_tests.py` 把套件数字、
  Chrome 版本、失败原因全发成 `::notice::` / `::error::`，并在有套件红时
  **自动重跑那一个套件、把 `FAIL` 行逐条发出来**。
  正是这一步直接给出了出错的断言名，否则只能看到"exit code 1"。

### 外部交叉校验

导出的 DXF/SVG/CSV 另用一个**独立实现**的 Python 解析器做第三方校验，
共 **2484 项全部一致**（18 组场景：5 个 build 型家具 + 8 个 panels 型配方 +
清单模式 + 图片两种模式 + 一组 finger/fillet 对比）。刻意不复用任何 JS 逻辑 ——
DXF 解析、带 bulge 的精确面积、含圆弧极值点的包围盒、RFC4180 CSV 解析全部用 Python
重写一遍，只比对最终数值。于是"两套独立实现算出同一结果"才能说明算得对：

- DXF：section 顺序、`EOF` 结尾、`CUT` 图层、轮廓数 = Σ(1+孔数)、全部闭合、无 NaN
- 逐零件：包围盒、含挖孔净面积、**外轮廓 CCW / 孔 CW**、孔不越出板边
- kerf：每件都严格外扩；**直角件精确 +0.4**；`面积增量 ≈ 周长 × kerf/2`（与顶点形状无关的普适不变量）
- SVG：无 NaN、mm 单位、`evenodd`、path 数 = 零件数 + pocket 数、所有路径闭合、
  pocket 用虚线且 `<title>` 里的深度值逐个对上
- CSV：表头 12 列完全一致、BOM、列数一致、引号字段解析，
  逐行核对 数量/板厚/纹理/通孔数/铣槽数/切割周长/备注，面积不含 pocket
- **POCKET 图层**：实体数 = pocket 数、`D<深度>` 文字标注值对上、环面积独立算一遍对上、
  落在零件轮廓内、kerf 时**面积变小**（证明是内缩而非外扩）
- **洞洞板**：从 DXF 里挑出 234 个 Ø12 圆，验证每个直径 = 12、行列间距恒 = 40、
  阵列左右上下都居中、全部在板内；净面积 = 板 − 四角 R20 − 234 孔
- **四角不变量**：`notch` 减 `s²`、`chamfer` 减 `s²/2`、`round` 减 `s²−πs²/4`
- **三类孔**：净面积 = 板 − 圆 − 圆角矩形 − 腰形（三个解析式独立算）
- **边部切口**：净面积 = 板 − Σ缺口；切割周长 = 矩形周长 + 2×Σ深度
- **井字酒格装配语义**：从 DXF 轮廓上量出每处半槽，验证槽宽 = `t+fit`、
  槽位 = 对方板标高、每块板只从单侧切入、且**两块板的开口在相反侧**
  （这类错误几何全合法，`validate()` 查不出来，只能靠装配断言）
- 图片模式：立牌高 = 目标高 + 板厚（榫头额外伸出）、底座宽、每层都有销孔、
  层面积逐层递减、DXF 中确实含 bulge 圆弧
- **带弧样式的弧归属**：`recipeBench` 同时导 `fillet` 与 `finger` 两版，用 Python
  重算弧面积与包围盒。这一组当场独立拦住了 `mirrorProf` 的 bulge 归属缺陷
  （变异测试时报 `recipeBench/横撑 高 147.416 vs 118.000`）—— 这类"不报错只是弧切错"
  的隐病，只有拿第二套实现重算才盯得住

## 与板材下料工具（慧切 cutlist 等）的关系

参考 [smartcuttech.com/cutlist](https://www.smartcuttech.com/cutlist) 这类工具重做了自定义交互。
两者定位不同，本工具是**在它们的下料清单能力之上再加一层榫卯结构求解**：

| | 板材下料工具 | 本工具 |
|---|---|---|
| 输入 | 零件清单（长×宽×数量×工艺） | 清单 / 结构配方 / 板位表 / **上传图片** |
| 加工特征 | 孔、槽、洞洞板、切口、定深铣槽 | 同上（本版补齐） |
| 纹理方向 | 支持，约束排样 | 同上（本版补齐） |
| 实测板厚 | 支持厚度偏差录入 | 同上（本版补齐） |
| **榫卯结构** | 不涉及（靠五金连接） | **自动求交并布置搭接/通榫/指接，含配合间隙** |
| **装配验证** | — | 逐个量出榫与槽的实际间隙、验证半槽开口方向 |
| 排样 | 支持 | 支持（含纹理锁定） |
| 运行方式 | 在线服务 | **纯前端离线，双击 HTML 即可** |

也就是说：只想切几块板 + 打几个孔，两者能力相当（本工具离线、免注册）；
想让板子**互相咬合、不用五金**，则需要榫卯求解与配合验证这一层。

## 已知范围

- 排样以**包围盒**为单位（不做凹形嵌套），利用率保守但绝不重叠
- 3D 预览已改为**真轮廓沿板厚挤出**（榫头/榫眼/指接齿在 3D 里看得见），
  但仍不做干涉检查；配合的精确性由 test-mate 的数值验证保证
- **导出路径**只能选"文件夹句柄"，拿不到绝对路径字符串（浏览器沙箱限制，
  没有任何 API 能把 `D:\xxx` 告诉网页）；`file://` 直开时此 API 不可用，
  会自动降级到默认下载目录并在按钮 `title` 里说清原因
- 16 种配方中有 5 种（箱体/书架/抽屉/格架/桌凳）**无法转成板位表**（异形板 /
  四角互补哬合），参数只能在左侧面板里改，那个按钮会置灰并说清原因
- 图片模式不做矢量布尔运算：所有"加榫头/开槽"都在**位图掩膜**上做，之后统一追踪，
  拓扑变化（开槽把件切成两半）由追踪器自然处理。代价是精度受掩膜分辨率限制
- 上传图片长边超过 900px 会自动降采样（保证描摹速度）
- 桌/凳采用板式腿架方案（适合板材），非传统方腿框架
- 导出前请按实测板厚调整"板厚"与"配合间隙"——海洋板标称 15mm 常有 ±0.5mm 偏差，
  建议先用小料试切一组榫卯校准 `fit`（**现已支持直接填"实测板厚"自动补偿**，
  但仍建议试切一次确认 `fit`：不同刀具、不同进给的实际余量差别不小）
- 定深铣槽只支持**矩形（可圆角）**，且必须用 CNC/雕刻机；激光切不出定深槽
- 一条板边只能承担一种接合。若设计上过约束，程序会降级并提示，
  被放弃的那几处需要改用木销或自攻螺丝——这是几何限制，不是 bug
- 图片生成的立牌/叠层件，建议先按 1:1 打印纸样比对再上机

## 部署到 GitHub Pages

纯静态、无构建、无依赖 —— 把仓库丢上去开个 Pages 就能用。

### 一行命令

```powershell
python tools\publish.py marine-ply-diy
# 然后粘上令牌、回车
```

它会依次完成：验证令牌 → 建仓（已存在则复用）→ `push -u origin main`
→ 开 Pages（分支 `main` / 目录 `/`）→ **轮询直到站点真的能打开**，
最后还会逐个拉 `app/index.html`、`app/js/joints.js`、`app/tests/index.html`
确认资源没 404。

> 为什么要轮询而不是 push 完就报成功：Pages 首次构建要 1–2 分钟，
> 这段时间内 URL 返回 404。"推上去了"不等于"网站能访问"，
> 后者才是需求，所以验收标准定在后者。

### 令牌怎么给、为何这么给

`publish.py` **本身不含任何密钥**，可以安心入仓。令牌的路径是：

| 环节 | 做法 | 为什么 |
|---|---|---|
| 输入 | `stdin` 读一行 | 写在命令行会进 PowerShell 历史（`ConsoleHost_history.txt`） |
| 传给 git | `GIT_ASKPASS` 回调本脚本自己 | 不用把 `https://user:token@github.com/...` 写进 remote |
| remote | 干净 `https://github.com/<user>/<repo>.git` | 带凭据的 URL 会永久落在 `.git/config` 里 |
| 缓存 | `-c credential.helper=`（置空） | 防止 Windows 凭据管理器默默存下来 |
| 日志 | 所有输出过 `mask()` | git 报错信息里真的会带上完整 URL |

需要的权限：classic token 勾 `repo`；或 fine-grained 给
Contents / Pages / Administration 三项 Read+Write（Administration 只为建仓，
仓库已存在可不给）。

> ⚠ **令牌一旦公开贴出就当作已泄露处理**。GitHub 有秘钥扫描，
> 公开粘贴过的 `ghp_...` 会被自动吊销，再拿去调 API 只会得到
> `401 Bad credentials`。遇到这个报错不是脚本错了，是该重新签一个。

### 仓库名建议用 ASCII

中文仓库名（如"海洋板DIY"）GitHub 允许，但 Pages 域名会被 punycode 成
`xn--...` 的形状，分享链接很难看。`publish.py` 建仓后会**以 GitHub 返回的
真实 `name` 为准**重算 remote 与站点地址（GitHub 会对仓库名做归一化，
押注"我传什么就是什么"会把两个地址全算错）。

另外：**GitHub Pages 免费版要求仓库 public**（private 需 Pro）。

### 手动推也可以

```powershell
git remote add origin https://github.com/<你的帐号>/marine-ply-diy.git
git push -u origin main
# 然后 GitHub → Settings → Pages → Source: Deploy from a branch
#                        → Branch: main / 目录: / (root) → Save
```

### CI：push 就跑全部测试

`.github/workflows/tests.yml` 在 ubuntu 上装 headless Chrome、起一个
`python3 -m http.server`，照样跑 11 套件 + 2484 项外部交叉校验。

它**不只看"FAILS 0"**。这是个真实的坑：套件中途抛异常时根本不会写出
TOTAL 行，"页面里没有 FAIL 字样"于是会被误当成通过。所以
`tools/ci_run_tests.py` 同时卡三条硬指标：

1. 套件数必须 **= 11**（缺一个就红）
2. **每个**套件的断言数 >= 基线（防"只跑了前三条就抛异常"）
3. 总断言数 >= **1848**；另外单独查启动自检 `59/59` 和根重定向

这三条做过变异验证：把 `test-visual` 基线从 147 改成 200（模拟断言变少），
脚本当场 `rc=1` 并同时报出"断言数 147 < 基线 200"与"总断言数不足"两条。
